# HAMMER2 on Linux: the implementation and integration plan

The plan for taking HAMMER2 from "create, check, read" on this platform to
the flagship root filesystem the specification names, integrated into the
storage model (specification section 27) rather than beside it. Written
2026-08-25 by the specification session on the five H0 deliverables in this
directory and on the storage proposal's stages (documents 02, 04, 07, 09 in
the specification repository's `proposals/saxum_filesystem/`). It is a plan
with exit criteria, not a schedule; every stage says what it produces in this
tree, what gate proves it, what it depends on, and who does it.

## Goal and shape

An out-of-tree Linux kernel module, `hammer2.ko`, built against the kernel
this system runs and packaged as `linuxPackages.hammer2` exactly as
`linuxPackages.zfs` is, carrying the DragonFly core's format and algorithm
files and rewriting the OS-facing files the way every BSD port already has
(`HAMMER2_PORTABILITY_AUDIT.md`); a storage-model backend adapter that
declares HAMMER2's capabilities honestly at every stage (27.3); and, at the
end, a root filesystem that passes the same conformance suite as OpenZFS and
Btrfs (document 07 section 8, the flagship qualification gate). The BSD
license permits in-tree submission later; the strategy spends that only after
qualification (`HAMMER2_UPSTREAM_STRATEGY.md`).

Two things the plan holds fixed from the proposal: no write path before the
archaeology and the read-only driver exist, and no relaxed test standard for
the flagship. And one thing James set on 2026-08-25: this track is the
storage program's priority, with OpenZFS holding the root until it qualifies.

## The stages, with what each produces here

Each stage's exit criterion is the proposal's; the deliverables and gates are
this tree's.

### H0 Archaeology: done 2026-08-25

Reading 1 of H1's three, done the same day (`H1_READING_1_SPIN_AUDIT.md`,
their 05ac973): no acquire site sleeps under the lock, so `rw_semaphore`
is legal everywhere; one site, `hammer2_chain_repchange` at
`hammer2_chain.c:2324`, takes `reptrack->spin` and releases it on no path
in all four trees, staged as a question for Dillon and carried with a
provenance note; and the DIO layer must complete bios into a workqueue,
which constrains reading 2.

The documents in this directory. Remaining inside H0 by the audit's own
"open" lists: nothing, and that reading was itself incomplete by a
dependency class the lists could not contain: the BSD `sys/tree.h` and
`sys/queue.h` macro headers, not files in any HAMMER2 tree and so invisible
to file-level provenance, surfaced when `hammer2.h` was written
(2026-08-25) and are vendored; the second section of
`H0_VENDORED_LIBRARIES.md` records it. The provenance CSV generator landed 2026-08-25
(`scripts/hammer2-provenance.py`, H1's first task), and the `sys/libkern`
helper resolved to one stock CRC-32C file needing no clone
(`H0_VENDORED_LIBRARIES.md`). The vendored-library
question closed 2026-08-25 (`H0_VENDORED_LIBRARIES.md`, their 6859a29):
xxHash is stock, proved by the vendored copy returning the published XXH64
reference for the empty string under `test-hammer2-checkalg.sh` with a
negative control; LZ4's decompressor is stock behind HAMMER2's four-byte
framing, so H1 carries no LZ4 and its compressor is H2's call-site work;
zlib is the same library under a prefix with a workspace argument at three
init sites. The module uses the kernel's own three.

### H1 Read-only driver

Exit: mounts DragonFly-created media read-only; superblock and volume
discovery, root lookup, directory traversal, file reads, xattrs if the format
carries them, PFS and snapshot discovery, `stat` and `statfs`, clean unmount;
passes the F1 and F2 fixtures and detects the F3 corruptions without
modifying media.

Produces: the package building a loadable `hammer2.ko` against the pinned
kernel; the shim (`hammer2_linux.h`, the mechanical families from the API
map); the DIO layer, one folio per `hammer2_io` in the block device's page
cache, which `sb_set_blocksize(sb, HAMMER2_PBUFSIZE)` makes 64 KiB folios
(reading 2; `hammer2_io.c` written 2026-08-25, their f35c107); the
VFS entry for the read side (`fs_context`, `super_operations`,
`inode_operations` lookup and getattr, `iterate_shared`, `read_folio`);
synchronous XOPs as the FreeBSD port does; and the read-only test that mounts
each fixture and compares against its manifest.

First week, before any estimate is written (the API map names these):
the per-site audit of the 69 `hammer2_spin_*` acquire sites (177 was a token count) for sleeping under
the lock; the DIO buffer-ownership design; the diff of the algorithm files
with the shim's renames normalized, to know exactly which lines of `chain`,
`flush`, `freemap`, `bulkfree` and `inode` are carried.

Gate: `scripts/test-hammer2-linux-ro.sh` (new): builds the module, boots a
guest with it, mounts every F1 and F2 fixture, verifies manifests, exits 2
without a guest. Registered in the shared CI runner with the expensive-half
marking.

Before that gate can exist, the cheap half is `scripts/test-hammer2-io.sh`
(their f35c107, registered): `-fsyntax-only` with the kernel's clang
against the pinned kernel's `dev` output, which compiles nothing and so
stays inside the standing order. Two rules it learned bind every harness
this plan describes that compiles against kernel headers by hand, the
F-series fixture runs included. The 7.x headers need the kernel's
`CC_FLAGS_DIALECT` (`-fms-extensions`), read from the `dev` output's
`.config` as `CONFIG_CC_MS_EXTENSIONS` and never hard-coded; without it
`fs.h`'s own `static_assert` fails and every check reads FAIL uniformly,
which is the shape of a harness bug and not of a finding. And a control
on kernel code is not a `-D` on the command line: `blkdev.h` defines
`BLK_MAX_BLOCK_SIZE` after any such flag and the "ceiling guard fires"
check passed while asserting nothing. A control is a prefix header
included AFTER the kernel header it subverts, and both of that gate's
controls are now that shape.

Depends on: nothing in the storage program; the fleet's DragonFly guest for
F2 (James's call to boot it).

### H2 Minimal write

Exit: create, write, truncate, directory mutation, unlink, rename, metadata
mutation, sync and flush, clean unmount; F4 round trips both ways with
DragonFly.

Produces: the write side of the VFS entry (`write_begin`/`write_end` or
iomap, `create`, `mkdir`, `unlink`, `rename`, `setattr`), the flush path
through the DIO layer's dirty tracking, the freemap allocation path carried
from the core, and the format fuzzing corpus the test spec requires before
any writable root (F3 as seed).

Gate: the read-only gate extended with the F4 round trip and the fuzz corpus
run.

Depends on: H1; a FreeBSD or DragonFly guest for the round-trip verification.

### H3 Crash recovery

Exit: survives the crash matrix (kill, panic, power-off, torn metadata)
during writes, with mount-time recovery converging to a committed state and
`fsck_hammer2` agreeing.

Produces: the recovery path on mount, F5 fixtures, and the first capability
declaration a storage-model profile could accept for a non-root domain.

Gate: the crash matrix from the test spec run in QEMU with a disposable
block device, calibrated first against the FreeBSD port.

Depends on: H2; the storage program's reference backend and crash harness
(epic S3) if they exist by then, otherwise a HAMMER2-local harness that S3
later absorbs.

### H4 Snapshots and checkpoints

Exit: the backend adapter implements `prepare_checkpoint`, `verify`,
`make_durable`, `activate`, `rollback`, `release` and `list_recovery_points`
on HAMMER2 snapshots, and passes the universal snapshot conformance suite.

Produces: the adapter, and the ioctl surface redesigned as Linux ioctls
(the API map's "interface redesign" row).

Depends on: the storage program's S1 (model) and S3 (reference backend) as
the oracle; this is where the track and the program meet, and the plan does
not let H4 start before S1 to S3 exist, because an adapter written against
no model is a second model.

### H5 PFS as storage domains

Exit: the specification's domains (SYSTEM, STORE, PERSISTENT, BUILD, CACHE,
RECOVERY, BOOT) map to PFS roots, derived from archaeology and workload
testing rather than assumed; the installer lays them down through the
adapter, with the partition page display-only for this backend
(`docs/installer.md`).

Depends on: H4; the installer's backend selection by declaration (0.3).

### H6 Nix-scale hardening

Exit: million-file trees, parallel builds, store GC, snapshots retained under
churn, low memory and near-capacity, all passing; F6.

Depends on: H5; the build host, which is the only machine with the workload.

### H7 Advanced storage

Multi-device, replication, remote checkpoints, clustering (the subsystems
every port dropped). Investigate; not required for flagship qualification.

### Qualification

Document 07 section 8's eight demonstrations plus the test spec's
qualification gate, and only then the root on HAMMER2 and the roadmap's 1.0
storage decision. Until then OpenZFS holds the root, by James's ruling.

## Integration with the storage program's order

The program's epics run S0 to S8 (model, registry, reference backend,
OpenZFS, Btrfs, Nix and boot integration, resource safety, compatibility
backends) before S9 to S14 (this track). The priority James set moves H1 to
H3 forward: they need nothing from S1 to S8 and can run alongside them. H4
is the join and waits for S1 to S3. That is the whole ordering rule of this
plan. It is not the proposal's: document 09 says S10 does not start before
S1 to S7 have executable tests, and James's priority overrides that rule for
H1 to H3.

## Who does what

- **Implementation session**: every stage's code, package, gate and fixture
  generation; the H1 estimate after the first-week readings; the toolchain
  package corrections the license audit names (`meta.license`, the
  `USE_EXFAT` comment).
- **Specification session**: the audits and this plan; the specification's
  capability declaration for HAMMER2 (27.9) updated at each stage from the
  gate's measurement, never ahead of it; the relay of upstream findings; the
  filing drafts for James.
- **James**: whether and when the BSD guests boot for fixtures; the H1
  estimate's acceptance; every upstream contact; the 1.0 storage decision.

## Decisions this plan takes, and the ones it leaves

Taken, from the precedents: synchronous XOPs (FreeBSD's choice) for H1 to
H3; the physical buffers live in the block device's page cache as 64 KiB
folios rather than in a DIO-owned pool (reading 2 superseded the plan's
first answer, and `sb_set_blocksize` ending in
`mapping_set_folio_min_order` was re-read at v7.2 `block/bdev.c` on
2026-08-25); `rw_semaphore` as the default
lock with `spinlock_t` only where the audit shows atomic context; Linux's own
LZ4, xxHash and zlib if the vendored copies prove unmodified; no clustering
files imported before H7.

Left, with the trigger that decides each: a workqueue-backed XOP pool
(measured against synchronous on F6); iomap versus classic address-space
operations for file data (decided in H2 by what a maintainer would ask for,
which is iomap, unless the format's 64 KiB physical buffers argue otherwise);
in-tree submission (after qualification).

## Risks, each with its instrument

- The two deep concerns are larger than the ports suggest: the first-week
  readings size them before an estimate exists.
- Format drift between `makefs` output and kernel output: the F1 against F2
  file-by-file comparison in H1.
- A dialect rather than the format: F4's round trip with DragonFly in H2.
- Provenance: the generated CSV, and the import rule that no file enters
  without a row.
- Attention: nothing goes to Kusumi or Dillon before H0's questions are
  answered from source, and nothing to `linux-fsdevel` before a fixture suite
  passes.
